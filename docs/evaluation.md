# TaskFlow Agent 评测体系

将 TaskFlow Agent 作为 **执行型产品** 评测，而非仅评测「摘要读起来是否流畅」。面向 MVP 验证与版本对比：**假设—指标—数据集—门槛—失败模式—迭代闭环**。

---

## 1. 评测总目标

**核心问题：** 在碎片办公输入下，Agent 是否 **更快**（时间 ROI）、**更省力**（少改写）、**更可一键采用**（零编辑即可过），帮助用户得到 **可执行任务与可沉淀资产**？

---

## 2. 产品假设与对应证据

| ID | 假设 | 主要证据类型 |
|----|------|----------------|
| H1 | 使用 Agent 较纯手工路径更快完成「可用任务清单」，且更易「零编辑通过」 | `T_manual`、`T_agent`、时间节省率；无修正批准率（辅助印证） |
| H2 | 降低关键任务漏召（尤其隐含交办） | Recall、漏召清单 |
| H3 | Agent 产出是否降低「认可与改写」摩擦，而非只做更像话的摘要 | 采纳率、字段编辑率、有用性评分（辅助） |
| H4 | 模拟工具动作有助于理解「执行型」价值 | 定性访谈、产品理解度问卷 |
| H5 | 周报素材减少回溯时间 | 草稿耗时、人工核对与改写成本 |

---

## 3. 评测维度与指标字典

### 3.1 任务抽取质量（Extraction）

任务抽取既是模型能力问题，更是 **办公执行场景下的交付质量** 问题：评测上区分三层——**基础分项**回答「准不准、全不全」，**综合聚合**给出整体诊断，**业务保障**对齐「关键事项不能漏」的产品底线。避免将多项指标平行堆砌；上级指标由下级推导或约束。

#### （一）一级｜基础分项指标

刻画单次抽取在标注集上的 **原子能力**：精确性与完整性分工明确，不设额外衍生指标，以免稀释主线。

| 指标 | 定义 | 作用 |
|------|------|------|
| **Precision** | 模型产出任务中，**确为真实任务**（与 Gold 对齐或可接受等价合并）的比例 | 衡量 **准确性**：列表里有多少是「真活儿」，直接关系用户纠错成本与信任 |
| **Recall** | Gold 任务集合中，被模型 **成功检出**（匹配到对应 Gold 项）的比例 | 衡量 **完整性**：有多少真实交办被捞出来，直接关系漏事与跟进风险 |


#### （二）二级｜综合聚合指标

在 Precision 与 Recall **已知** 的前提下，用单一数值概括「抽取模块整体好坏」，用于版本对比与回归摘要。

| 指标 | 定义 | 作用 |
|------|------|------|
| **F1 Score** | Precision 与 Recall 的 **调和平均**：`F1 = 2 × P × R / (P + R)`（P、R 均为 0 时需约定处理方式） | **综合诊断**：在准与全之间不做主观加权时，给出可比的总体抽取水平 |

**说明：** F1 **不作为与 Precision、Recall 并列的第三类基础能力**；它是二级 **聚合结果**。汇报顺序建议：**先分项 → 再给出 F1**；解读时若 F1 高但 Recall 低，仍应指向「完整性风险」，而非被单一分数掩盖。

#### （三）三级｜业务保障指标

对齐真实办公后果：**漏掉一条闲聊误判**与 **漏掉一条老板点名截止事项** 不对称。因此在全量 Recall 之外，单独约束 **高优先级 / 关键任务子集**。

| 指标 | 定义 | 作用 |
|------|------|------|
| **P0 / 关键任务 Recall** | 在标注为 **P0（或等价「关键」）** 的 Gold 任务子集上计算的 Recall：该类任务中被成功检出的比例 | **业务保障**：确保最易造成事故或违约的事项 **不被遗漏**，体现产品对办公场景后果的优先级判断 |

### 3.2 执行有用性（Usefulness）

「有用」在产品里最终要落到 **执行成本是否下降**：用户是否愿意留下系统生成的任务，以及为「可用」要付出多少改写成本。MVP 阶段只保留 **可稳定打点、口径清晰** 的少数指标，形成 **用户认可 → 修改成本 → 主观验证** 的闭环；拆解细化、歧义提示等不作为本维度 KPI，避免追踪分叉与口径争议。

#### 核心行为结果

- **采纳率（Acceptance Rate）**

| 项目 | 说明 |
|------|------|
| **定义** | 用户 **未删除且最终保留** 的候选任务占 **当期产出候选任务总数** 的比例 |
| **作用** | 衡量用户对系统生成任务的 **真实认可度**，是执行有用性的 **核心结果指标** |
| **打点建议** | 以「确认闸门」提交时的任务列表为准：删除记 0、保留记 1；批量丢弃按任务条数计 |

#### 核心修改成本

- **字段编辑率（Field Edit Rate）**

| 项目 | 说明 |
|------|------|
| **定义** | 用户对 **已保留** 任务在关键字段（如 `title`、`deadline`、`owner`，与 MVP 表单对齐）上发生 **任意有效修改** 的任务占比；可再拆 **分字段编辑率** 定位短板 |
| **作用** | 衡量任务结构化质量与用户改写负担：**编辑越少，默认草稿越省力**，直接支撑「低修改成本」的产品叙事 |
| **说明** | 分字段是为了诊断（标题糊、时间猜错、责任人错配），不是再叠一层 KPI；阶段汇报优先 **整体字段编辑率 + 最高频被改的 1～2 个字段** |

#### 辅助主观验证

- **有用性评分（Usefulness Score）**

| 项目 | 说明 |
|------|------|
| **定义** | 小规模测试中用户对任务/清单「是否 **可直接开工**」的 **5 分 Likert** |
| **作用** | 补充 **主观体验**，解释采纳率与编辑率之外的态度信号（例如「留了但仍别扭」） |
| **定位** | **非核心长期监控指标**：适用于小样本可用性测试；是否进入线上仪表盘视样本量与投放稳定性而定 |

**本节刻意不包含：** 拆解子步骤编辑率、歧义提示帮助度——MVP 实现与埋点复杂、边界易模糊，易与抽取/拆解质检纠缠；若后续需要，再在独立版本中定义口径。

### 3.3 整体执行效率（Execution Efficiency）

本维度用 **最少指标** 验证两件事：**相较人工 Baseline 的效率收益（ROI）**，以及 **清单是否「可直接过」**。不展开主观信任量表、拷贝次数或交互机制评测——MVP 阶段难稳定闭环、易稀释叙事。

**价值验证框架：**

| 问题 | 对应指标 |
|------|----------|
| **是否更快** | `T_manual`、`T_agent`、**时间节省率** |
| **是否更省力（时间 ROI）** | 同上；与纯手工路径对比同一完成标准 |
| **是否可直接通过** | **无修正批准率**（多少任务 **零编辑** 即可批准） |

与 §3.2 分工：**字段编辑率** 刻画「改了哪些关键字段」；本节 **无修正批准率** 刻画「整条任务能否不改就过」——若产品流程为「先编后批」，二者通常 **强相关**，汇报时可并列披露，用其一作主 KPI 亦可。

#### 时间效率提升

- **`T_manual`**（Manual Baseline Time）

| 项目 | 说明 |
|------|------|
| **定义** | **同等输入条件**下，用户 **完全手动** 整理出一份可用任务列表（与产品侧约定的完成标准一致）所耗费时间 |
| **作用** | 建立 **人工 Baseline**，后续一切「提速」均相对该口径对比，避免自说自话 |

- **`T_agent`**（Agent-assisted Time）

| 项目 | 说明 |
|------|------|
| **定义** | 用户使用本产品完成 **同一输入** 下的任务整理——含浏览候选、**必要确认与编辑**——直至输出达到与 `T_manual` **相同的完成标准** 所耗费时间 |
| **作用** | 衡量 **真实端到端耗时**，反映产品在实际工作方式下的效率 |

- **时间节省率（Time Savings Rate）**

| 项目 | 说明 |
|------|------|
| **定义** | `(T_manual - T_agent) / T_manual`（`T_manual = 0` 时约定处理方式或剔除无效样本） |
| **作用** | **单一 ROI 指标**：把提速幅度转成可对比的量化语言，便于版本迭代对照 |

**测试建议：** A/B 使用 **同质难度、结构相近** 的两份材料（或同一份材料的轮换次序平衡学习效应）；统一发令起点（材料完整呈现）与终点（清单达标示意）。

#### 最终执行质量

- **无修正批准率（Zero-Edit Approval Rate）**

| 项目 | 说明 |
|------|------|
| **定义** | 系统生成的任务中，**无需任何字段编辑** 即可被用户 **直接批准通过** 的任务条数占比（口径与 MVP「批准」动作对齐：通过即进入下游或视为定稿） |
| **作用** | 把「模型 + 交互」的 **综合可用性** 压成一个可追踪结果：**越高说明默认草稿越可靠**，与省时、省力同向；建议与 §3.2 **字段编辑率** 同屏对照，定位「字段级改写」与「整任务零编辑通过」是否一致 |

**本节不包含：** 拷贝步骤数、置信度校准、控制感量表及各类机制类描述——主观性强或埋点碎片化，不利于 MVP 形成干净闭环。

### 3.4 价值主张可理解度（以 User Workspace 为主场景）

面向目标用户或内部干系人的小样本问卷；**问卷与「是否像摘要」的观察** 默认基于 **用户端** 路径。指标与 Gold 对照的权威呈现归 **Admin Console**，见 [demo_plan.md](./demo_plan.md) §2、§4。

- 能否说出核心痛点句？  
- 能否说出与摘要工具的 **一个** 本质差异？  
- 能否复述闭环 **5 步**（输入→分类→确认→拆解→模拟沉淀）？

## 4. 标注规范（Gold Label）

### 4.1 标注单元

- **任务：** 最小可指派工作单元；允许合并同一语义重复句。  
- **非任务：** 闲聊、纯粹背景、仅提问无交办。  
- **隐含任务：** 无「请」「安排」等显性动词但语境明确——**必须单列**，用于测 Recall。

### 4.2 每条 Gold 任务建议字段

`title, evidence_span, owner_gold (可空), deadline_gold (可空), priority_gold (可空), criticality (P0/P1)`

### 4.3 一致性

双人标注 **Cohen's Kappa** 或简单一致率；争议样本第三方裁定。正式报告中可注明：「Kappa≈0.xx（样本量 n）」。

## 5. 测试数据集规模（MVP 建议）

| 类型 | 数量 | 用途 |
|------|------|------|
| 纯群聊 | 5 | 抽取 + 噪声 |
| 纯会议纪要 | 5 | 分类 + 行动项 |
| 混合 bundle | 3 | 端到端、与原型 Fixture 同源 |
| 文档节选 | 3 | 长句截止与责任人 |

**总计：** 约 16 条 scenario；每条含人工 Gold。**样本求可解释、可复现**，规模可按阶段调整。

## 6. 可用性测试流程（建议）

**参与者：** 初级执行向 5 人 + 项目负责人向 2 人（若可行）。

**任务：**

1. Scenario A：限时手工抽取任务列表（录音停表）。  
2. Scenario B：同质难度输入使用 TaskFlow（允许编辑）。  
3. 填写短问卷（有用性评分等辅助项）。  
4. 半结构化追问：「你会在哪个真实场景打开它？」

**记录：** 漏召列表、误报列表、卡点界面、原话引用（脱敏）。

## 7. 成功门槛（MVP 参考阈值）

以下为 **阶段参考阈值**，非行业基准；可按实测调整并在文档中脚注。抽取模块建议 **先看 P0 Recall，再看分项 P/R，最后带一句 F1 作为汇总**，避免唯综合分数论。

| 维度 | 建议阈值 |
|------|----------|
| P0 / 关键任务 Recall（三级） | ≥ 80% |
| Precision / Recall（一级） | 分项如实披露；二者权衡需在个案中解释 |
| F1 Score（二级） | 作版本对比参考，不设单独「达标线」亦可 |
| 采纳率（复审后） | ≥ 70% |
| 字段编辑率 | MVP 以 **分项披露** 为主；优化迭代时可设分字段上限（如标题编辑率下降趋势） |
| 时间节省率（§3.3） | ≥ 30%（相对 `T_manual`） |
| 无修正批准率（§3.3） | MVP 以 **披露 + 版本对比** 为主；据此制定迭代目标 |
| 有用性评分（5 分制，辅助） | 均值 ≥ 4.0（仅在有可用性测试样本时报告） |

若未达标：须如实记录并列出对应迭代项（见 §9）。

## 8. 失败模式清单（必须跟踪）

| 模式 | 表现 | 关联 Skill |
|------|------|------------|
| 闲聊当任务 | FP 上升 | S2, S3 |
| 隐含任务漏召 | FN 上升 | S3 |
| 截止 / 责任人幻觉 | 批准前大量改写、`T_agent` 被拉长 | S3, S4, S8 |
| 拆解空泛 | 定性反馈差或拆解步骤被跳过 | S5 |
| 周报无证据 | 沉淀价值弱 | S7 |
| 过度自信 / 默认值差 | 无修正批准率低且耗时优势不明显 | S3, S4, UI |

## 9. 迭代闭环（指标 → 动作）

| 若… | 则优先… |
|------|---------|
| Recall 低 | 补强隐含任务 few-shot；扩充混合 bundle |
| FP 高 | 收紧 Task 判定；强化分类边界 |
| 字段编辑率高 | 优先定位高频被改字段；校正抽取/优先级提示与默认值策略 |
| 无修正批准率低 | 与字段编辑率对照定位：抽取字段质量 vs 交互摩擦；优化默认值与澄清文案 |
| 产品被感知为「仅摘要」 | 强化模拟执行与 Before/After 等执行链可见性 |

---

## 10. 汇报与对齐要点

- 抽取评测拆三层：**P/R** 看准与全，**F1** 为之上综合诊断，不作第三个并列 KPI。  
- 业务侧重点披露 **P0 / 关键任务 Recall**，说明漏关键交办风险。  
- 有用性并列 **采纳率** 与 **字段编辑率**：保留比例与改写负担。  
- **§3.3** ROI：`T_manual` / `T_agent`、**时间节省率**、**无修正批准率** 口径一致披露。  
- 评测集与 Web 原型 **同源 fixture**，指标与界面引用数据一致。
