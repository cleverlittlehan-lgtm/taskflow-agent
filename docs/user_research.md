# TaskFlow Agent 用户调研报告

> **文档性质：** MVP 阶段用户访谈与桌面研究整理。结论来自半结构化访谈、流程还原与竞品对照；样本为当前轮次可触达用户，量化结论与 [evaluation.md](./evaluation.md) 同口径补齐。

---

## 1. 调研目标

### 1.1 商业与产品问题

1. 「碎片信息」是否构成 **高频、高痛** 的执行问题，而非一次性整理负担？  
2. 用户当前 **自建工作流** 的卡点在哪里：脑记、备忘录、表格、Notion、项目工具等如何串不起来？  
3. 现有 AI / 效率工具（会议摘要、通用对话）为何 **停在总结层**，无法满足「推进工作」？  
4. MVP 应优先切入哪类角色与场景，才能 **最快验证闭环** 并支撑产品叙事一致性？

### 1.2 待验证假设（与研究问题对应）

| ID | 假设 |
|----|------|
| H-R1 | 初级执行岗在多通道交办下，**任务遗漏与周报回溯**是最可感知的痛点。 |
| H-R2 | 用户更需要 **结构化任务 + 可同步载体**，而非更长篇幅的摘要。 |
| H-R3 | 「自动建任务 / 结构化看板更新」类能力比「文笔更好的纪要」更能表达差异化价值。 |

## 2. 研究方法与设计

### 2.1 方法组合

| 方法 | 用途 | 样本 |
|------|------|------|
| 半结构化用户访谈 | 挖掘行为、工具栈、痛点优先级 | 初级执行向用户 5 人；协作 / 负责人向用户 2 人 |
| 工作流程还原 | 抽象共性链路「接收 → 判断 → 记录 → 同步 → 汇报」 | 基于 **访谈原话与行为描述** 归纳 |
| 竞品 / 替代方案桌面研究 | 对比「摘要工具」与「执行型 Agent」差异 | 会议 AI、IM 置顶、手动表格等 |

### 2.2 招募与筛选标准

- **P1：** 每周 ≥3 次从 IM / 会议接收交办；使用 ≥2 种工具管理待办或进度。  
- **P2：** 每周需输出周报或同步文档。  
- **排除：** 无协作交办的一线城市远程兼职等弱相关样本。

### 2.3 伦理与数据说明

可公开的调研材料均经 **脱敏处理**；若引用原话或行为细节，遵循知情同意与数据最小化原则。

## 3. 用户分层与切入策略

### 3.1 分段定义

| 分段 | 角色示例 | 痛点重心 | MVP 角色 |
|------|----------|----------|----------|
| **A 初级执行层** | 实习生、新入职执行岗、产品助理、运营 / 项目助理 | 漏任务、多工具抄写、周报回溯 | **主叙事** |
| **B 中层协作层** | PM、项目经理、运营负责人、CS、顾问 | action items 清理、跨团队同步成本 | 次要场景 |
| **C 管理协作层** | Team Leader、部门负责人 | 跟进可见度、复盘材料组织 | 路线图，非 MVP |

### 3.2 为何 MVP 聚焦 A

- 痛点 **强度高、频次高**，叙事直观。  
- 工作任务 **同质性强**，便于设计固定样本数据与评测集。  
- 初级执行向用户在实习与项目场景中 **触达成本可控**，便于 **后续扩大样本与职能覆盖**。

## 4. Persona（画像摘要）

### 4.1 Persona A：产品运营实习生「小林」

| 维度 | 描述 |
|------|------|
| 上下文 | 同时参与多个项目；上级在群里随手交办；纪要分散在文档与 IM |
| 工具链 | 飞书 / 企微、Excel / Notion、个人待办 |
| 典型路径 | 看到消息 → 判断是否任务 → 复制到表格或备忘录 → 周末写周报前翻记录 |
| 情绪句 | 「群里说一句我就得记着，不记就容易漏」「周报最痛苦是翻聊天记录」「AI 能总结，但还是要我一个一个建任务」 |

### 4.2 Persona B：产品经理 / 项目负责人「阿辰」

- 会后 **整理 action items** 耗时；许多任务难在 **同步与跟进** 而非难度本身。  
- 引用：「要的是自动推进，不是再多一个总结工具。」

### 4.3 Persona C：团队 Leader「周姐」

- 痛点在 **落地与跟进**，而非信息不够。  
- 引用：「不是缺信息，是缺执行落地。」

## 5. 关键洞察（分层表述）

洞察与 PRD、workflow 的对应关系如下。

### 5.1 行为层（用户在做什么）

共性链路：**信息接收 → 人工解读是否为任务 → 手动录入工具 → 手动同步进度 → 汇报前再次聚合**。链路长、重复环节多，任一环节懈怠即产生遗漏或延迟。

### 5.2 态度层（用户怎么说）

- 对「更长纪要」疲劳；对「帮我列出我要做的事」期待高。  
- **信任与可控：** 欢迎自动整理与结构化草稿，但要可追溯、**显式确认** 后再写入任务与项目列表；风险类更新要 **高亮并二次确认**，拒绝静默覆盖。  
- 直接支撑 **Confirmation Gate**、证据链与 MVP 期 **Mock**，真实接入后置。

### 5.3 场景层（哪里最痛）

| 场景 | 典型失败 | 产品映射 |
|------|----------|----------|
| 群聊交办 | 淹没在闲聊、无责任人时间 | 任务抽取 + 缺失字段标注 |
| 会议纪要 | 决议与任务混在一起 | 上下文分类 + 任务结构化 |
| 周报 | 回溯成本高 | 周报素材 Skill + 证据链 |

### 5.4 根因归纳（一句话）

**最大矛盾不是「没有记录信息」，而是「碎片信息 → 可执行状态」的转化效率过低且高度依赖人工。**

### 5.5 洞察 → 当前产品设计（简链）

调研结论与 [PRD.md](./PRD.md)、[workflow.md](./workflow.md) 中的落地关系：

| 用户反馈 / 洞察 | 设计落点 |
|-----------------|----------|
| 漏任务、多通道交办 | **Task Extraction** + 证据与置信度，把「可指派单元」稳定捞出 |
| 要草稿但要可控、要可追溯 | **Confirmation Gate** + 证据链；未确认不进入执行 |
| 「总结有了，任务还得自己建」 | **Tool Calling + Workflow Sync**：进 Tasks / Projects，不停在对话层 |
| 周报前翻记录成本极高 | **周报素材** `generate_weekly_report_material`，PRD 列为 P1，聚合已确认上下文 |
| 要点散落、难复用 | **知识卡片**，PRD 列为 P1，绑定已确认执行 |
| 工程与范围约束 | **Mock Execution（MVP）** 先验证闭环；企业权限、多系统编排等 **Non-Goals** |

访谈里最常被提的三件事是 **漏任务、碎片整理、周报回溯**。版本上 P0 先做 **抽取 → 路由 → 确认 → Mock → Tasks/Projects**，把防漏和抄写成本打穿；周报素材与知识沉淀在 P1，与 PRD 一致；重协作与组织级能力进路线图，避免拖垮第一版闭环。

## 6. 竞品与替代方案（简述）

**主线差异：** 多数工具停在 **「摘要 / 理解信息」**；用户访谈中反复出现的需求是 **「执行转化」**——把碎片变成 **可指派对象、可确认动作、可进 Tasks/Projects 的状态**。

| 类型 | 用户怎么用 | 缺口 |
|------|------------|------|
| IM 自带置顶 / 收藏 | 手工标记重要消息 | 无结构化、无拆解、无汇报聚合 |
| 会议 AI 摘要 | 一键生成纪要 | **摘要工具**：读懂会议 ≠ 建好任务；**执行侧**仍靠人工一条条录入与跟进 |
| 通用 LLM | 粘贴文本求总结 | **对话式摘要**：无稳定 schema、无 **用户确认后** 的工具载荷与 **工作流视图** 沉淀 |
| **TaskFlow（执行型 Agent）** | 同一输入优先产出 **可指派任务 / 项目更新 + 证据链 + 确认后执行 + Sync 视图** | **执行转化优先**；MVP 以本地 Mock 验证闭环，生产写回见路线图 |

## 7. 洞察 → 需求映射

| 洞察 | 产品需求（PRD 对齐） | 工作流 / Skills |
|------|----------------------|------------------|
| 漏任务 | 抽取 + 置信度 + 证据 | Task Extraction；Review & Ambiguity |
| 二次整理成本高 | 分类非任务噪声、可执行切片 | Recognition + Task / Project 路径分流 |
| 不知如何下手 | 字段补齐与路由前校验（可选增强：拆解子步骤） | Field Extraction；PRD 路线图项可单列 |
| 周报回溯痛苦 | 已确认上下文 → 周报素材（P1） | `generate_weekly_report_material`；知识卡片 P1 |
| 不信任自动写入 / 风险敏感 | 确认闸门 + Mock + 高风险二次确认 | Confirmation Gate；`update_project_board` Risk 路径 |

## 8. 访谈提纲

**A. 背景**  
角色与协作方式；任务主要来自哪些通道；是否多项目并行。

**B. 当前流程**  
临时交办如何记录；常用待办工具；会后如何整理行动项；周报如何产出。

**C. 痛点**  
最易遗漏什么；整理 / 拆解是否耗时；现有 AI 工具哪里不满意。

**D. 概念验证**  
若有一个助手可「识别任务、拆解、建议优先级、生成待办与周报草稿」，**最先**用在哪个场景；最看重防遗漏、拆解、同步还是汇报。

## 9. 假设验证与产品闭环

### 9.1 关键假设的验证状态

| 假设 | 当前支撑 | 仍待验证 |
|------|----------|----------|
| H-R1 漏任务与周报回溯最痛 | 多段访谈原话与 Persona、场景表一致 | 漏召率、时间节省需 evaluation 样本与试用数据 |
| H-R2 更需要可执行任务而非长摘要 | 态度层与竞品对照一致 | 不同职能是否同样排序 |
| H-R3 执行类能力比「更好纪要」更有感 | Persona B 引用与桌面研究一致 | 真实二选一或采纳率 |

### 9.2 设计决策与证据强度

- **证据较强、可直接写进 MVP：** Confirmation Gate、证据与置信度字段、先 Mock 再接外部写入，与访谈中的可控与谨慎表述一致。  
- **仍带假设、需数据跟进：** P1 周报与知识在叙事中的权重；若试用中周报场景反响弱，产品与文档叙事向 P0 闭环收缩，P1 资源后移。  
- **若核心指标持续不达标：** 不扩写未验证能力；优先收紧范围为 P0、加强确认前提示与评测集，再谈扩展。

### 9.3 局限与下一步

定性为主、样本有限；端到端耗时、编辑率、漏召等按 [evaluation.md](./evaluation.md) 补。后续扩大访谈、做手动对照计时的可用性小测，评测集标注能对齐则记入 evaluation 注脚。
